### §3-2 scale-to-fit 舞台裡的 @dnd-kit → **真的會偏，偏多少量出來了；修法也驗過**

用一個最小的 Vite probe（`probe/dnd.tsx`，只有 5 個 sortable 方塊、外層 `transform: scale(0.6)`，
無專案程式碼）＋ CDP 真滑鼠事件實跑：

```
未修正（scale = 0.6）
  指標從 cx 288.8 走到 288.8+132 = 420.8（螢幕 px）
  dnd-kit 寫進 style 的 transform：translateX(132px)  ← 直接把「螢幕位移」當成 local 位移
  卡片實際落點 screenCx = 368.0                        ← 螢幕上只走了 132 × 0.6 = 79.2px
  → 卡片跟不上手指，差 52.8px
  但 **落點判定是對的**：order A,B,C,D,E → B,C,A,D,E
  （碰撞偵測吃的是 getBoundingClientRect，已經是螢幕座標，所以只有「視覺跟隨」壞掉）

修正後（在 sortable 元件裡把 transform 除以舞台倍率）
  卡片實際落點 screenCx = 420.8   ← 與指標完全重合，lag = 0.0px
  鄰居 B、C 各左移一個節距（354.8→288.8）
  order A,B,C,D,E → B,C,A,D,E
```

**採用的修法**：不是 dnd-kit 的 `modifiers`。`modifiers` 只作用在拖曳中的那一個節點，
而 `SortableContext` 給鄰居的位移也是從 client rect（已縮放）算出來的、同樣會偏；
所以改在 `MiniCard` 裡統一除以倍率（`Stage.tsx` 的 `useStageScale()`），拖的那張與讓位的鄰居一起修好。

**查證途中另外揪到一個 spec 沒寫、但一定會壞的東西**（見 §5-1）：
framer-motion 的 `animate={{ scale }}` 會接管同一個元素的 `transform`，把 dnd-kit 寫的位移整個蓋掉。
第一次在真的 app 上量到「手指走到 348.9、卡片停在原地 164.9」（lag 184px）就是這個。
改成**外層純 div 管拖曳、內層 motion.div 管彈跳**之後：

```
[1024×768] scale=0.8678  pointerTargetCx=348.9  draggedCardCx=348.9  lag=0.0px  opacity=0.4
           鄰居 g2 164.9 / g3 256.9 各讓一位   order g1,g2,g3,g4 → g2,g3,g1,g4（localStorage 同步）
[1366×1024] scale=1.1576 pointerTargetCx=465.4 draggedCardCx=465.4  lag=0.0px  opacity=0.4
           order g1,g2,g3,g4 → g2,g3,g1,g4
```

**倍率放大（1.1576）與縮小（0.8678）兩邊都是 0.0px**，而且拖完照樣點得動
（`G_clickStillWorks = ["ㄋ","ㄧ","三聲","你"]`），`PointerSensor { distance: 5 }` 不用調。

### §3-3 iPad Safari 的 speechSynthesis 語音名稱 → **退路全部還活著；iPad 本身標「需人工」**

本機沒有 iPad，所以我做的是**把 iPad 上可能出現的語音清單餵給真的 `pickVoice()` 跑**
（probe 直接 import `src/lib/speech.ts`，不是抄一份）：

| 假想清單 | `pickVoice` 選到 | `voiceReadsBopomofo` | `shouldUseCharReading` |
|---|---|---|---|
| iOS 中文名 `美佳 / zh-TW` | 美佳 | true | false |
| iOS 英文名 `Meijia / zh-TW` | Meijia | true | false |
| `Meijia (Enhanced) / zh-TW` | Meijia (Enhanced) | true | false |
| 底線寫法 `Meijia / zh_TW` | Meijia | true | false |
| 沒有美佳、有 `Li-Mu / zh-TW` local | Li-Mu | false | **true**（退回代字） |
| 沒有美佳、zh-TW 只有雲端 | Li-Mu（local=false） | false | **true** |
| 只有 `Ting-Ting / zh-CN` | Ting-Ting | false | **true** |

| 空清單 | null | false | **true** |

`PREFERRED_VOICE_PATTERNS = [/美佳/, /Meijia/i]` 兩種寫法都命中，
`(Enhanced)` 這種後綴也命中（比對用的是 `RegExp.test`，不是相等）；
退路 **zh-TW local → zh-TW → zh → null** 逐段確認仍會走到，
而且**任何一段沒命中美佳就自動打開代字讀音**，不會出現「選錯語音全程無聲」。

順帶記錄本機（macOS 26.1 / Chrome）真的清單第一個就是 `美佳`，所以驗收時走的是符號路徑
（`B_spoken = ["ㄇ","ㄠ","一聲","貓"]`，不是代字）。

我沒有 iPad 無法實測。**這是本期唯一沒被機器驗到的行為。**

### §3-4 `apple-mobile-web-app-capable` 全螢幕下的 100vh / safe-area → **用 `100dvh` ＋ `env()`，Chrome iPad 模擬三種尺寸都不捲動**

做法：`.stage-box`（`position: fixed; inset: 0; height: 100dvh;`
`padding: env(safe-area-inset-top) env(safe-area-inset-right) env(safe-area-inset-bottom) env(safe-area-inset-left)`）
量自己的 `clientWidth/clientHeight` 當「可用空間」，`ResizeObserver` ＋ `visualViewport.resize`
＋ `orientationchange` 三路觸發重算。這樣瀏海、Home indicator、Safari 網址列的伸縮全部自動算進去，
不用在任何地方寫死數字。

Chrome 裝置模擬（`mobile: true`, `landscapePrimary`）實測：

```
1180×820   dvh=820px  dvw=1180px  safe-area top/left = 0px  box 1180×820  scale 1.0000
1024×768                                                     box 1024×768  scale 0.8678
1366×1024                                                    box 1366×1024 scale 1.1576
body overflow = hidden
```

meta 全部到位：`apple-mobile-web-app-capable=yes`、`apple-mobile-web-app-status-bar-style=black-translucent`、
`viewport = width=device-width, initial-scale=1, maximum-scale=1, user-scalable=no, viewport-fit=cover`、
`apple-touch-icon = ./icon-180.png`、`<title> = ㄅㄆㄇ`。

**限制講明白**：Chrome 的裝置模擬**不會注入真的 safe-area inset**（量到 0px），
所以「瀏海底下不會被切」這件事我只驗到「程式有在讀 `env()` 且讀得到值」，
真機上讓出來多少**要 iPad 上看一次**（併入 §4-7 的人工項）。

## 5. 順手抓到、但 spec 沒寫的兩件事

1. **framer-motion 蓋掉 dnd-kit 的 transform**（已修，見 §3-2）。
   這在第二／三期的 `MiniCard` 就是同樣的寫法——當時的驗收只量了 `opacity` 與拖曳前後的順序，
   **沒有量拖曳中卡片的螢幕座標**，所以「卡片不跟手」一直沒被抓到（順序是對的，因為碰撞偵測走 client rect）。
   換句話說：這不是搬家搬壞的，是**本來就壞、這次才量到**。修法寫在 `MiniCard.tsx` 的註解裡。
2. **`vite.config.ts` 需要顯式 `resolve.alias`**：`tsconfig.json` 的 `paths` 只影響型別檢查，
   dev server 解析 `@/...` 會 500。`yarn build` 反而過得去（打包器自己吃了 tsconfig），
   所以**只跑 build 是驗不出來的**——一定要真的開頁。
